# Iron Ridge — V1.0 Plan

This plan covers the six V1.0 items from the owner's comment on PR #4. Each one has a
design, an implementation step small enough to hand to one agent, and a
definition of done. The "V1 assumptions" listed under each item continue the
numbering style of `V0.9_ASSUMPTIONS.md`.

---

## 1. Commanders move on the sub-grid

**How it works**

- An `Army` becomes a **commander**. Its position is a **sub-hex** (`pos`). `at`
  (main hex) is still stored, but it is derived from `pos` and always kept in sync, so
  ownership, income and warning clocks keep working unchanged.
- **Movement:** each turn a commander gets `commandMove` sub-hex steps. Each step
  costs 1, and the path is found by BFS over the world's sub-cells. Friendly and
  enemy commanders, garrisons and off-map cells block movement. The default is
  `2·subRadius + 1`, about one main hex, so the pace matches V0.9 at every grid size.
  "Forced march" (every unit has move ≥ 5) doubles it.
- **Capture:** a commander that ends a step inside an unowned or enemy main hex
  with no enemy holder in it takes that hex. This uses the existing `capture()`.
- **Engagement:** a commander can attack an enemy commander or garrison whose
  sub-hex is within `engageRange` (default `subRadius`). The battle's contested main
  hex is the defender's main hex. The origin is the attacker's main hex. If both are
  in the same main hex, the origin is the neighbouring main hex the attacker
  approached from. The attack costs the same CP as before.
- **Strategic line of sight:** commanders and garrisons see enemy holders within
  `sightRange` sub-hexes (default `3·subRadius`). The check reuses the tactical
  `lineOfSight` over the terrain height map, with eye height 1.5. Owned territory
  still gives adjacency vision, as in V0.9. `visibleArmies` switches to this rule.
- All strategic constants move into one `COMMAND` table next to `ECONOMY`.

## 2. Garrisons: recruits go to the building

- A holder has `kind: 'commander' | 'garrison'`. A garrison belongs to a
  **building**. In V1.0 the only building is the HQ. A garrison's `pos` is the
  building's sub-hex (the HQ main-hex centre), and it never moves.
- `recruit` always adds the unit to the recruiting team's HQ garrison, up to
  `garrisonCap` (default 12). It never creates a commander.
- At game start each HQ has an empty garrison plus one commander holding
  `STARTING_ARMY`, placed on a free sub-hex next to the HQ.
- A garrison is a legal attack target. When a battle is fought over its main hex,
  the garrison defends. Elimination checks count a garrison with units as "has
  forces".

## 3. Assigning units and seeing what's inside

- **Actions:**
  - `transferUnits { fromId, toId, unitIds }` moves units between two of the
    active team's holders.
  - `formCommander { fromId, unitIds }` splits units off a garrison or commander
    into a new commander on the nearest free sub-hex.
  - A holder left with no units is removed. A garrison is never removed.
- **Reassignment rule:** holders are eligible for a transfer when they are within
  `transferRadius` sub-hexes (default `subRadius`) **and** in the same main hex.
  Both checks default on for commanders and buildings, and each can be switched
  off in the rule config (`TransferRule { radius, sameMainHex }`).
- Capacity still applies: a commander holds at most `armyCap`, a garrison at most
  `garrisonCap`. Units moved into a commander don't give it extra moves. It keeps
  `min(movesLeft)` of the two holders.
- **UI:** when you select a commander or building on the strategic map, a
  **Contents** panel lists each unit with its type, label and HP bar, plus
  checkboxes. Its actions are **Transfer to ▸** (only eligible holders are listed)
  and **New commander**. Eligible holders are highlighted on the map while you
  have units selected.

## 4. Micro combat simulator (battle container)

This lives in the engine at `packages/engine/src/sim/`. It uses no DOM and runs in
Node or a Web Worker.

- **`BattleSpec`** (JSON) describes one test:
  - `era`
  - `attacker` and `defender`: each a list of `{ typeId, count, hp? }`
  - `terrain`: `flat | slope | ridge | seeded` (+ `seed`)
  - `forts?`
  - `objective?`
  - `maxRounds`
  - `rules?` (unit/mechanics overrides, see §5)
  - `expect?`: `{ winner: 'attacker' | 'defender' | 'even', tolerance }`
- **Grid build step, `sizeBattleGrid(spec, ruleset)`:** uses the game's own grid
  rules (`validateConfig` bounds, `deploymentZone` capacity, weapon ranges) to pick
  the **smallest** `GridConfig` where:
  - both forces fit their deploy zones;
  - the longest weapon range in the spec fits inside the battle footprint.
- **`BattleRuleset` interface:** `sizeGrid`, `buildTerrain`, `createBattle`,
  `stepAi`, `isOver`. Iron Ridge is the first implementation. A future game adapts
  the container by supplying its own ruleset.
- **Running:**
  - `runBattle(spec, seed)` runs AI vs AI and returns `{ winner, rounds, endReason, survivors, hpLeft }`. The same seed always gives the same result.
  - `runSeries(spec, runs, seedBase)` returns win rates.
- **Scenario library:** `packages/engine/scenarios/*.json`, about 8 standard
  matchups (tank vs AT gun, MG vs rifles, cav charge vs spears, archers vs infantry,
  mortar vs dug-in rifles, mirror matches that should come out even, …).
- **CLI:** `pnpm --filter @iron-ridge/engine sim [scenario…] --runs N [--rules overrides.json] [--compare]`
  runs headless on Node 22 with native type stripping.
- **Budget:** one micro battle should take under about 250 ms, so a 50-run series
  finishes in seconds.

## 5. Balance lab (dev-only tuning mode)

- **Runtime rule overrides (engine):**
  - `RulesOverride = { units?: Record<typeId, Partial<UnitStats>>, mechanics?: Partial<Mechanics> }`.
  - `withRules(override, fn)` swaps the active table synchronously, and `unitType()`
    merges the overrides.
  - `GameSettings.rules?` stores them in the game, and `apply()` wraps every action
    in `withRules(state.settings.rules)`. A game started with overrides therefore
    stays consistent after a save and reload.
  - `mechanics` exposes the main combat constants (`BASE_TN`, facing mods,
    `BLIND_FIRE_TN`, `MAX_FORT`, …) plus `ECONOMY` / `COMMAND`.
- **Screen:** shown only when `import.meta.env.DEV` or `?lab`. You reach it from
  the setup screen via **BALANCE LAB**.
  - A grid of unit cards. Each card renders the three.js model to a thumbnail
    through a shared offscreen renderer.
  - Every stat is an editable field: hp, move, vision, min/max range, direct and
    splash dice, splash radius, cost, climb, eye, and special-rule flags. Each card
    has its own **Save**.
  - **Apply all** saves the draft to `localStorage` (`iron-ridge-balance-v1`). New
    games (and **Restart with rules**) use it through `settings.rules`, with no
    rebuild.
  - **Export JSON** and **Reset** buttons.
- **Test:** runs the scenario subset in a **Web Worker** (headless). Each
  scenario runs once with the baseline rules and once with the draft rules. The
  result is a percent chart per scenario:
  - attacker-win % for old vs new;
  - the target band from `expect`;
  - a pass/fail flag.

  The same comparison is available from the CLI with `--compare`.

## 6. Save and load, fully tested

- **Engine `save.ts`:**
  - A save is an envelope: `{ format: 'iron-ridge-save', schema: N, engineVersion, savedAt, label, state }`.
  - `serialize`, `deserialize`, `validate` (structural guard) and `migrate` (a
    chain of schema steps). Migrations cover:
    - legacy 0.9 bare `GameState`;
    - `revealed` → `exposed`;
    - a missing battle objective;
    - V0.9 armies → commanders with `pos` and `kind`, plus HQ garrisons.
  - The logic moves out of `useGameStore` so it can be tested headless.
- **Web:**
  - An autosave slot plus 3 manual slots.
  - **Save** in the game menu.
  - A **Load** list on the setup screen, showing label, turn, phase and date.
  - **Export** / **Import** of a `.json` file.
  - A corrupt save is rejected with a visible message and never crashes the app.
- **Standard save fixtures**, in `packages/engine/fixtures/saves/`:
  - `strategic-t1`, `strategic-midgame`
  - `battle-pending`, `battle-deploy`, `battle-combat`, `battle-over`
  - `hotseat-fog`, `with-rules-override`
  - `legacy-0.9.0`, `corrupt`
- **Journey tests, engine:** for each fixture, load it, check that it validates,
  then play it to the end with AI for both sides. Every step must keep the
  invariants: no holder overlaps, `at` matches `pos`, and no negative CP.
  Round-trip equality is also tested, and so is determinism: a game saved and
  loaded mid-way ends the same as one played straight through.
- **Journey tests, web:** these run as store-level vitest with jsdom. They cover:
  - continue from each fixture;
  - the hotseat handoff shown on resume;
  - slot save/load/delete;
  - import/export;
  - rejecting a corrupt save.

  One Playwright smoke run in Chromium covers new game → save → reload page →
  continue.

## V1 assumptions — command layer

Step A (engine only). Code: `packages/engine/src/command.ts`, `strategic.ts`,
`types.ts`, `ai/strategicAi.ts`; tests in `command.test.ts`.

- **[V1-A1] Holders.** `Army` gains `kind: 'commander' | 'garrison'`, `pos` (sub-hex key)
  and, for garrisons, `building: 'hq'`. `at` is always the main hex containing `pos`;
  every write goes through `setHolderPos(world, army, pos)`. `Holder` is a type alias
  of `Army`, so the V0.9 name keeps working.
- **[V1-A2] Tunables.** `COMMAND` sits next to `ECONOMY` in `strategic.ts`. Distances
  are functions of the sub-radius n:
  - `commandMove(n) = 2n+1`. Forced march (every unit has move ≥ 5) multiplies it by 2.
  - `engageRange(n) = n`
  - `sightRange(n) = 3n`, `sightEye = 1.5`
  - `transferRule(n) = { radius: n, sameMainHex: true }`
  - `garrisonCap = 12`. `ECONOMY.armyCap = 8` still limits commanders.
- **[V1-A3] Transfer-rule config.** `GameSettings.transferRule?: Partial<TransferRule>`
  overrides the default for one game. `radius: null` turns the radius check off, and
  `sameMainHex: false` turns the main-hex check off.
- **[V1-A4] Occupancy.** A holder occupies its cell while it has units. A garrison
  always occupies its cell, even when empty. Two holders never share a cell. Movement
  BFS goes around every other holder, friend or foe, and around off-map cells.
- **[V1-A5] Movement.** `movesLeft` counts sub-hex steps. A move can stop on any
  reachable cell and spends exactly the BFS step count. The rest of the budget can be
  used later in the same turn. Garrisons have 0 moves.
- **[V1-A6] Capture.** A commander takes only the main hex it **ends** a move in, and only
  when that hex isn't already its own and holds no enemy holder with units. Main hexes
  it passes through are **not** taken. An empty enemy garrison does not stop a capture,
  so walking into an unguarded HQ wins, as in V0.9.
- **[V1-A7] Engagement.** `engage { armyId, targetId }` needs all of the following:
  - the attacker is a commander with at least 1 move left;
  - the target is an enemy holder with units, within `engageRange` sub-hexes;
  - the target is visible to the attacker's team (`visibleArmies`);
  - the team has `attackCost` CP.

  The battle is fought over the defender's main hex. The origin is the attacker's main
  hex when it is adjacent. Otherwise (same main hex) it is the defender's neighbouring
  main hex whose centre is closest to the attacker. With range n, the two holders are
  always in the same or adjacent main hexes. Garrisons cannot start attacks.
- **[V1-A8] Battle outcome.**
  - A beaten **garrison** loses all its units. The garrison object stays on its cell.
  - A beaten **commander** falls back to the free cell nearest it in an adjacent
    friendly main hex that has no enemy holders. If there is none, its survivors are
    lost.
  - A winning attacker moves to the free cell nearest it in the target main hex, or in
    the origin on EXTRACT, and captures the target. If another enemy holder with units
    is still in the target, the attacker stays put and nothing is captured.
- **[V1-A9] Strategic fog.** Each viewer sees:
  - its own holders;
  - enemy holders within `sightRange` of any of its holders, garrisons included, where
    the tactical `lineOfSight` from eye height 1.5 over `heightAt` is not blocked
    ("marginal" counts as seen);
  - enemy holders within one main hex of owned territory (V0.9 adjacency).

  Holders no longer give adjacency vision; LOS replaces it. With `fog: false`, every
  present holder is visible, empty garrisons included.
- **[V1-A10] Garrisons and recruiting.** `createGame` makes one commander with
  `STARTING_ARMY` on the HQ-centre neighbour facing the enemy HQ, and an empty HQ
  garrison on the HQ centre. `recruit` always adds to the HQ garrison and fails when it
  holds `garrisonCap` units. Garrisons are never removed. Commanders are removed as soon
  as they are empty.
- **[V1-A11] Elimination** counts units in any holder, garrisons included.
- **[V1-A12] Warning clocks** now also tick when an enemy holder is **inside** one of
  our main hexes (distance ≤ 1, was == 1). A commander can now stand in an enemy hex
  without taking it.
- **[V1-A13] Transfers.**
  - `transferUnits` / `formCommander` only work in the strategic phase, for the active
    team, with valid, unique unit ids.
  - The receiver's cap applies: `armyCap` for a commander, `garrisonCap` for a garrison.
  - A receiving commander keeps `min(movesLeft)` of the two holders. A garrison counts
    as 0, so units taken from a garrison can't move this turn.
  - `formCommander` puts the new commander on the free cell nearest the source, inside
    the same main hex. It fails if there is none. The new commander starts with 0 moves
    when formed from a garrison, or with the parent's `movesLeft` when split from a
    commander.
  - A commander can't give all of its units to a new commander; use `transferUnits` to
    merge instead.
- **[V1-A14] V0.9 adapter.** `moveArmy { armyId, dest: mainKey }` and `canMoveTo` still
  work. If an enemy holder is in `dest` and in engage range, the order engages it.
  Otherwise the commander moves to the reachable cell closest to that enemy, or, with
  no enemy there, to the cell of `dest` it can reach in the fewest steps.
- **[V1-A15] AI.** The AI:
  - recruits into the garrison, with a reserve rule like V0.9's;
  - engages the in-range target with the best odds at or above its threshold;
  - otherwise steps to the reachable cell scoring best on V0.9-style terms: progress
    toward its goal (in main-hex units), unheld ground, getting in range of a
    beatable enemy, avoiding stronger stacks;
  - musters spare garrison units by topping up a spent commander at HQ, or by forming
    a new commander once 4+ units are spare. It keeps 2 at home, and all of them when
    threatened.

  AI-vs-AI games finish in both eras with no illegal proposals. In a probe of 12
  games (2 eras × 2 grids × 3 seeds), each side won some.
- **[V1-A16] Not changed here.** `ENGINE_VERSION` stays `0.9.0`. Save migration of V0.9
  armies to holders is Step D. The web app got only the minimum it needs: garrisons
  get no army token, and the test helper picks commanders explicitly.
